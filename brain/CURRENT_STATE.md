## Known Issues
1. No audit records are written for authentication or authorization events. Login, logout, refresh, and any role, permission, or store-access change are not attributable in the audit trail, although AuditService already exists (02.11) and BR-007 makes such records immutable. Deferred by user decision; recorded as High finding H1.
2. No rate limiting or lockout on POST /auth/login. A password can be guessed without throttling. Deferred by user decision; recorded as High finding H2.
3. User and role hard-delete endpoints remain exposed (DELETE /users/:id, DELETE /roles/:id). Deleting a role cascades its permission grants out of every role that referenced it, which destroys authorization history. Deactivate exists alongside delete and is the safer path. Deferred by user decision; recorded as High finding H3.
4. JWT_SECRET is required but its strength is not validated at boot. Recorded as High finding H4.
5. The Flutter _RefreshInterceptor fails concurrent 401s instead of queueing them, which can sign a user out under parallel requests. It is a client robustness issue, not an authorization bypass. Recorded as High finding H5.
6. brain/CURRENT_STATE.md, brain/AUDIT_LOG.md, and brain/ASSUMPTIONS.md are stored with corrupted character encoding. Pre-existing, unrelated to auth, not repaired because a lossy repair would damage the audit history. See ASM-046 and High finding H6.

## Technical Debt
1. The store-access and permission repositories were typed as `any` end to end, which disabled type-level tenant checking. Corrected in 04.11, but the remaining repository interfaces elsewhere in the codebase have not been surveyed for the same pattern.
2. The auth guard chain lives in AuthModule rather than AppModule because AuthGuard depends on that module's JwtService. This is correct but subtle: moving it to AppModule would reintroduce a dependency-injection failure that is not obvious from the code.
3. Refresh-token expiry is only enforced at exchange time, never by a background job, so expired rows accumulate. Row count is bounded in practice by the TTL index but never reclaimed.

## Pending Decisions
1. ASM-044: the maximum duration a POS terminal may operate offline before it must refuse to trade is undecided. Deliberately not invented during 04.11. Must be resolved before Phase 11.
2. ASM-045: no documented policy exists for the initial password of a newly created account, nor for first-login rotation. During 04.11 the invented temporary-password behavior was removed and password is now required at creation. A password reset and forced-rotation flow is still undefined.
3. ASM-046: the corrupted encoding in three brain documents needs a dedicated repair task with per-file codepage analysis.
4. The permission catalog in brain/SECURITY.md has no read-permission codes. Reads of users, roles, and permissions are therefore gated by the matching manage code and fail closed. Category reads added in 05.01 follow the same pattern and are gated by `products:manage`. If distinct read and write permissions are wanted, that is a documented catalog change requiring a new brain/SECURITY.md entry and a seed update.
5. ASM-047: the category tree has no enforced maximum depth, by user decision. The ancestor-walk cycle check is iterative, so deep trees cost database round trips proportional to depth rather than failing. Revisit if a practical ceiling is ever required.
6. ASM-048: brands reuse the `products:manage` code from 05.01 rather than having their own, so catalog administration and product administration share one permission. Recorded rather than decided, because a permission code is a business-rule change. Revisit if catalog administration needs separating.
7. ASM-049: `Unit.precision` is read as decimal places and constrained to 0-3 in the DTO only, derived from the `NUMERIC(14,3)` quantity scale because no document defines the field. The database column is still an unconstrained `Int`, and nothing yet restricts lowering the precision of a unit that already has stock or history. Both need a documented rule and a check constraint.
8. ASM-050: the conversion multiplier is checked for `> 0` in the DTO and the service only, with no database CHECK constraint, and both unit foreign keys check existence rather than organization, so the service's organization check is the only barrier against a cross-tenant edge. Both should become database constraints once the conversion tables are otherwise stable. Also recorded there: direction is immutable after creation, so inverting a factor requires a delete plus a create.

9. ASM-051: every product route reuses `products:manage`, so `products:create`, `products:update`, and `products:deactivate` exist in the permission catalog but are unassigned, and one code governs both catalog and product administration. The organization check on each optional parent exists only in the service, with no database constraint preventing a future write path from attaching a product to a parent in another tenant. The product list also exposes no category, brand, or unit filter, which may be wanted once the catalog screen exists.

10. ASM-052: the at-most-one-primary rule is enforced in the service only, with no partial unique index (`WHERE is_primary`) on `product_barcodes`, so two concurrent promotions of different barcodes on one product could each commit a primary. The demotion and the promotion share a transaction, which rules out a half-applied state but not two interleaved ones. The 64-character value bound is a DTO choice rather than a column limit, and the `@@index([barcode])` on `product_barcodes` has no query behind it yet because scan lookup is deferred to 05.10 and 08.03. A per-store barcode scope is also undecided.
11. ASM-053: a rate change edits the tax category row in place, so the audit log is the only place a superseded rate survives; there is no append-only rate history, and a rate change is therefore not safe to perform without its audit record. The rate bounds are the `NUMERIC(14,4)` column scale enforced by a DTO pattern rather than a database `CHECK`, and the code uniqueness check is a service pre-check in front of the existing `@@unique([organizationId, code])`, so a lost race surfaces as a `P2002` rather than a 409. No exclusion constraint forbids two categories of the same code from having overlapping effective windows, because no brain document defines whether one code may have more than one window open at a time; only the ordering of each row's own window is enforced. Assigning a tax category to a product validates nothing about the category's status or window, since which rate applies to a transaction belongs to 14.03.

12. ASM-054: a price change is a retire plus an insert rather than an in-place edit, so those two requests are not atomic and a failure between them leaves the product with no price in force until the insert is retried. The overlap check runs inside the write transaction, but the schema cannot enforce it, so two concurrent inserts of overlapping windows on one product and price type can both commit; the composite index on (productId, priceType, effectiveFrom) keeps the check cheap, not serializable, which is the accepted cost of not adding a PostgreSQL exclusion constraint. Delete is limited to periods that have not started, so a mistake in a price that has already applied can only be corrected by closing the period and inserting a new one. Nothing requires a product to have any price at all, and the at-least-one-price check before selling has not been implemented, so a product can currently be offered with no price defined.

## Routes
All API routes are mounted under `/{API_PREFIX}/{API_VERSION}` (default `/api/v1`) via `configureApp()` (src/configure-app.ts), which also sets the JSON body parser limit from BODY_LIMIT. configureApp is used by main.ts and shared by all e2e suites. GET /api/v1 (Hello World), GET /api/v1/health (status ok).

Authentication is deny-by-default. An application-wide guard chain runs in the order AuthGuard, PermissionsGuard, TenantScopeGuard, and every route is authenticated unless it carries an explicit `@Public()` marker.

Public routes: `GET /api/v1`, `GET /api/v1/health`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`.

Protected management routes: `/api/v1/users` requires `users:manage`; `/api/v1/roles` and `/api/v1/permissions` require `roles:manage`; `/api/v1/store-access` requires `users:manage`; `/api/v1/categories`, `/api/v1/brands`, `/api/v1/units`, `/api/v1/products`, `/api/v1/tax-categories`, and the nested `/api/v1/products/:productId/barcodes` and `/api/v1/products/:productId/prices` routes require `products:manage` (ASM-051, ASM-052, ASM-053, ASM-054). All carry `@RequireTenantScope()`, and the organization is taken from the authenticated principal rather than from the request.

Category routes added in 05.01: `GET /api/v1/categories` (paged, filterable by `search`, `status` (active/inactive), and `parentId`; sortable on an allow-list of columns, defaulting to `createdAt` descending), `GET /api/v1/categories/:id`, `POST /api/v1/categories`, `PUT /api/v1/categories/:id`, `PUT /api/v1/categories/:id/deactivate`, `DELETE /api/v1/categories/:id`. Category names are unique per organization, enforced by the existing database constraint; a cross-organization id is reported as not found rather than forbidden, so existence is not disclosed across tenants.

Brand routes added in 05.02: `GET /api/v1/brands` (paged, filterable by `search` and `status`, sortable on an allow-list of columns, each row carrying a product reference count), `GET /api/v1/brands/:id`, `POST /api/v1/brands`, `PUT /api/v1/brands/:id`, `PUT /api/v1/brands/:id/deactivate`, `DELETE /api/v1/brands/:id`. Brands are flat, so there is no parent, re-parenting, or cycle logic. Brand names are unique per organization, enforced by the existing database constraint, and the same not-found-not-forbidden rule applies across tenants.

Unit routes added in 05.03: `GET /api/v1/units` (paged, filterable by `search` and `status`, sortable on an allow-list of columns, each row carrying product, conversion-from, and conversion-to reference counts), `GET /api/v1/units/:id`, `POST /api/v1/units`, `PUT /api/v1/units/:id`, `PUT /api/v1/units/:id/deactivate`, `DELETE /api/v1/units/:id`. `search` matches either the name or the code.
